## 已经实现的功能

## 本次任务

### 一、三张随机卡片的状态与补位（P0）
1. 在中央底部话语栏维持 **3个固定卡片容器/卡位**，各自维护 `slot_id`、当前 `word_id`、可用状态和独立刷新剩余时间。战斗开始时从该关可用预制话语池**随机抽取三条不同话语**，分别占据三槽。
2. **卡片在成功发表之前持续保留**当前话语，供玩家随时选择。点击一张可用卡只使其成为待发表的话语；随后点击中央棋盘任意有效位置，沿用 PB-06 的完整批次发表动作。
3. **发表成功的那一瞬间**，仅使用的卡位开始自己的 **5.0秒刷新倒计时**：该卡片暂时不可使用，保留旧卡的画面供倒计时展示；另外两个卡位保持现有话语与可用状态。
4. 5秒走完，**只替换该卡位**：从尚未由玩家本局主动发表过、也没有占据其它当前卡位的可用话语中随机抽取一张新卡；新卡出现后立即可使用，并清除该槽的进度显示。其余卡不重新抽取。
5. **三卡独立并行**：玩家可以连续使用 A/B/C 三槽并连续点击战场发表，**没有任何玩家全局发言冷却或公共发表间隔**。三槽可以同时处在5秒倒计时，也可以先后在不同时间完成补牌。
6. 保持 PB-06 既有“本场同一个 `word_id` 只能由玩家主动发表一次”的记录方式；抽牌池耗尽时，该槽显示明确的空槽/无可用话语状态并保持不可使用，其他未耗尽的卡位照常工作。随机抽牌复用当前词池与 RNG 入口，支持已有固定种子复现。

### 二、整卡填充的五秒进度表现（P0）
1. **进度表现覆盖整张卡片容器**。使用成功时填充进度从0开始，5秒内平滑增加到100%，用具有适当透明度的色块/遮罩直接填充整张卡片（建议从底向上填满），旧话语仍能辨认。
2. 倒计时期间，卡片明显处于不可用状态，继续显示原话、属性/强度等关键信息；倒计时结束时进度填满并立刻切换新话语、恢复常态。进度由实际剩余时间驱动，与卡位可用状态保持一致。
3. 三张卡片各自独立播放填充；选中态、鼠标悬停和数字键 1/2/3 选句沿用现有行为，冷却中的卡位不可选中。玩家已选中的卡位发表成功后清除待投放选中态，可立即选择另一张可用卡。
4. 保持现有中央话语栏尺寸和版式；程序化实现遮罩/填充动画，用真实 Godot 画面验证文本可读性及三卡同时倒计时的表现。

### 三、发表结果与倒计时的一致性（P0）
1. **仅 A 的实际发表成功事实启动指定卡位5秒刷新**。选择卡片、点击其它 UI、棋盘点击未成功、战场位置无效、单位容量不足及其他发表失败情况保留原卡位可用状态，不消耗这张卡、不启动刷新。
2. 玩家发表请求包含被使用的 `slot_id` 或由 A 可核验的等价卡位上下文，A 验证卡位当前可用且与待发表 `word_id` 对应。一次点击只允许对应卡位成功消耗一次，确保快速连发时每张卡只被扣一次。
3. **从玩家发表路径移除原全局5秒门控**，并由卡位状态管理刷新时机；对手 AI 的独立发言策略与时间配置继续采用当前 PB-06 实现，玩家三槽刷新规则只作用于玩家。
4. 暂停、继续、重新开局和战斗结束时，三个卡位的状态、计时与当前对局状态同步；暂停时倒计时暂停，重开时重置并重新发三卡；正常阶段退出后按现有流程关闭选句操作。
5. 保留 PB-06 已实现的强度1/2/3 → 2/4/8颗棋子、50/60/70%感染、克制/改口、PK、自动特性、对手反击与PK100%后的矛盾击破流程。

### 四、最小模块分工及交付
- **D（UI）**：在现有中央话语栏实现3个槽的可用/填充/换牌视觉、卡位选择与输入，接入 A 的成功/失败事实；用 Godot 实机截图或短录像展示三槽可同时冷却的效果。
- **A（战斗拥有者）**：修改玩家发表许可校验，去掉全局五秒发言冷却，新增/适配对卡位的一次性成功提交入口及5秒刷新生命周期；玩家快速连续发表和战斗暂停/结束状态正确。
- **C（词库）**：复用现有词定义、随机候选与一局一次性词池，对刷新槽提供“排除本场已发表词和其他槽已占用词”的随机补牌读取。
- **E（验证）**：只做这项改动所需的最小 Godot 功能回归和真人画面验收。
- 按各模块实际责任边界最小修改。各子任务单独 commit，按 `AGENTS.md` 形成 `docs/Integration/复读感染_PB-12_2026-10-18_log.md` 并同步本次确定性规则所影响的正式文档。

## 本卡验收标准（必须实际运行 Godot）
1. 开局三个卡槽各展示不同随机话语；不使用的卡持续留在原槽。
2. **连续快速发言**：A、B、C三槽全部可用时可以不间隔5秒连续发表三次；三次各调用 PB-06 既有强度批次生成，并分别启动自己的5秒倒计时。
3. 消耗A槽后，B/C槽立刻可用；A槽5秒后才换为随机新话，期间B/C槽内容保持不变。
4. A、B、C在不同时刻被用完，各自按照自己的5秒完成时间补牌；三张卡的**整卡填充**进度同时正确可见、文本可读且不遮挡棋盘。
5. 点击空白 UI、卡片选择后取消、无效落点或因棋子数量达到上限而发表失败：对应卡仍可用、没有刷新倒计时，也不消耗 `word_id`。
6. 补牌不能抽到本场已主动使用的 `word_id` 或其他占用卡位的 `word_id`；池耗尽时卡位清楚地呈现耗尽状态。
7. Godot 正常运行，无新增解析/场景错误；交付真实操作录像（至少展示快速连发3张、三张独立进度及5秒后逐一补位）、截图、验证记录和任务日志。

## Godot 开发环境
Godot：**4.7.2**；脚本：**GDScript**；工程根目录：当前 `Empty-start`（以 `project.godot` 实际确认）。
目标平台：Windows PC / Android；游戏基准1920×1080。Godot 工程操作：**Godot-MCP-Native**；Godot 官方文档：**godot_mcp**。

## 执行要求（依仓库任务卡模板）
### 1. 先检查当前项目状态
核对 branch、PR、未提交变更、`project.godot` 和当前游戏真实 scene tree、已存在的卡位/发表/冷却实现，确认模块和信号所有者后修改。
### 2. 严格控制任务范围
修改玩家话语卡位刷新与视觉所必需的代码、配置、回归验证和相关文档，保留已完成战斗。
### 3. 保持最小必要复杂度
优先在现有话语卡 UI 和战斗组织者中新增少量卡位状态、时间计算和抽牌请求。
### 4. 组合优于继承
复用现有 Godot 组件/场景、UI 和信号连接，按现有已验证组合方式管理卡片状态。
### 5. 保持场景边界
UI 管视觉和输入、A 管发表成功事实与冷却许可、C 管静态词定义/候选池；模块通过稳定入口交接。
### 6. 区分场景、逻辑和数据
卡片文本及强度沿用静态配置；运行时槽位和五秒计时属于当前战斗 UI/会话状态。
### 7. 新增实现前按顺序检查
优先复用当前抽牌、卡片显示、Tween/ProgressBar 与战斗发表结果接口，补足当前最小需求。
### 8. Godot API 不允许猜
针对项目实际引擎版本，通过 `godot_mcp` 查清 Tween、Control 裁切、进度绘制及必要 API 后实现。
### 9. 使用 Godot-MCP-Native 检查真实工程
检查真正 Scene Tree、按钮输入、信号与脚本连接，并运行观察三槽并行计时和棋盘投放。
### 10. 自动化与额外保障机制
复用现有测试与固定 seed；增加少量针对随机不重复、独立时间、失败不消耗的测试，其余通过真人验收。
### 11. 避免脆弱的 Godot 依赖
使用现有对外方法和 signal 交换槽位 ID/结果，保持 UI 与战斗内部逻辑解耦。
### 12. 修改现有场景时尊重现有结构
检查实例场景、UID、资源 owner 与现有信号；在原中央话语栏上增量增加覆盖层和状态展示。
### 13. 验证实际 Godot 行为
验证解析、场景可启动、三卡随机刷新、全局门控移除、有效/无效点击、暂停/重开及完整一局。
### 14. 完成前检查
复核全局玩家5秒门控确已移除、每个slot只有一个活动计时、发牌不重复、输入和资源不误扣、没有无用抽牌管理器或多余节点。
