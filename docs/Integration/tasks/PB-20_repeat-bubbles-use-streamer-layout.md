# PB-20 · 复读气泡沿用主播发言气泡的全文排版规则

优先级：**P0｜复读气泡可读性与统一布局**。Owner：**Lane D（正式气泡 UI）＋E（真实窗口验收）**；A 负责和 #276、PB-11 正式战斗代码合流。

状态：**2026-10-19 最新策划更正**。本卡覆盖 [PB-17](PB-17_bubble-per-component-fixed-width-and-autoheight.md) 中“团体人数→100/150/500px气泡宽度”的旧定义。用户明确要求：**复读气泡规则与主播发言气泡一样、宽度容纳约10个汉字才换行、文字区域居中放在气泡里、文字每行左对齐**。本任务卡不代表代码已完成。

## 已经实现的功能
- 主播发言气泡由 `StreamerBubbleView` 使用正式字体测量/真实 RichTextLabel 内容高度、自适应换行和字号下限；超出可用高度时保持完整原句并支持原生滚动。
- 团体复读气泡当前绘制在 `PlanBUnitField`，PB-17 候选按人数定宽（1人100、2人150、8人500），其 `draw_multiline_string()` 使用水平居中、最高26px字号；截图出现每行只有两三字的窄长气泡。
- PB-11 已有团体级计时、感染首次弹词/变词重新弹词、尾巴跟随成员、团体并合以及多人同框等行为。

## 本次任务
### 1. 复读与主播发言采用同一套文本排版逻辑
1. **以正式主播发言气泡的稳定机制为准**：完整原文、按实际字体测量文字栏宽度、自动换行、按全文计算高度、文字字号下限、局部可用高度限制及溢出时可阅读。复读气泡尽可能直接使用或参照现有 `StreamerBubbleView` 文本排版行为；只在确实可复用时提取最小布局辅助，不为共用新建复杂组件体系。
2. **当前主气泡的文字栏宽度统一以“10个全角汉字”作为视觉容量目标**，包括玩家与对手的主播发言主气泡和棋盘中单人/团体复读主气泡。依据同一字体、字号和左右内边距测量约10汉字宽度；中文常规文本应约在第11字换行，不再出现一行只有两三个汉字的窄长框。
3. 团体气泡主框宽度**不再随着1、2、8人的人数变化**。成员数只影响尾巴数量/位置、组归属和团体锚点；同一类主气泡宽度由文字容量决定，不因词长和人数横向剧烈变化。主播已有历史缩略气泡可以保留其历史视觉层级，但需同样保证原文可读取。
4. 保持中文标点自然换行和 Emoji/中英混排的完整字形；以**实际字形宽度**为准，不按 UTF-16 码元强切导致半个 Emoji/标点被截断。需以10字左右的中文实例明确展示测量结果。

### 2. 文字内容在气泡里居中摆放、每行左对齐
1. 气泡整体以发言者/团体锚点为中心选择合适位置，**文字块位于气泡框内部的居中安全区域**，具有一致上下左右 padding。
2. **每行文字必须左对齐**（Godot `HORIZONTAL_ALIGNMENT_LEFT` 或对应 RichTextLabel 水平排版），**不能把每一行居中**；短句可以占一行，长句自然换行，文字块高度按内容增高。
3. 排版规则对玩家复读、对手复读、团体复读和两侧主播当前台词一致；保留已有的队伍配色、漫画轮廓、P1/P2状态与气泡尾巴，表现资源可以因类别不同，但排版语义一致。
4. 保留任何真实话语原文，文本不可用省略号、只显示头两行、降低到不可辨字号等手段丢失。实际极端高度超出时沿用主播现成“完整文本+可阅读溢出”的行为与屏幕约束。

### 3. 安全区域和原有复读演出
1. 气泡靠近棋盘边缘、HUD和底部三张话语卡时使用已有局部定位/可用矩形约束，选择遮挡较少的位置，尾巴仍指向所代表的棋子；结合 PB-19 新64×64视觉半径对齐。
2. 继续使用团体级定时、首感染、变词刷新、P1/P2、成员合并及2～5尾等既有机制。只改变气泡排版，不改变复读发生时间、感染、话语数据和PK规则。
3. 文字测量在文案/宽度/字号改变时更新，运动中仅调整显示位置并尽量复用布局，避免增加每帧多次文字排版的负担。

### 4. 一次真实 Godot 视觉验收
1. D/E 提交一组来自正式场景的真实截图：**约5字、10字、11字及实际最长的正式话语**，至少覆盖单人复读和多人团体复读，展示相同宽度及不同高度；另展示一侧主播主泡，确认换行规则一致。
2. 同一张 1280×720 画面里检查气泡、HUD、棋子和底部三卡无严重遮挡，必要时再看1920×1080。允许对真正无法避让的位置记录实际原因，随后同卡定点修复。
3. 所有相关视觉 PR 正文嵌入真实截图，标注分辨率、SHA、字号与字宽策略；不重复长时间性能压测或无意义多轮冒烟。

## 验收标准
- 普通中文主气泡每行**能容纳约10个汉字**，第11字正常换行；文字安全区在框内居中，每行从左对齐，不再两三字一行。
- 玩家/对手主播主泡与单人/团体复读采用同类文字测量、换行、高度和全文保留规则；1人与8人团体主泡不会仅因人数变化而改变固定文字栏宽度。
- 长句、边缘位置与团体尾巴实际可读，整体可见；保留复读触发逻辑。PR 附真实 Godot 截图及测试代码 SHA。

- Godot 工程操作 MCP：**Godot-MCP-Native**；Godot 官方文档 MCP：**godot_mcp**。

检查真实 main/目标基线、分支、worktree、未提交代码、场景树、节点、资源、信号和现有任务 PR；基于最新真实实现接续。

只做本卡要求的局部功能，和其他 Owner 的交集由 A 统一接线，其他问题记录给对应任务。
### 3. 保持最小必要复杂度
优先复用当前 Godot 控件和绘制逻辑，可直接调整现有组件时不重建新框架。
### 4. 组合优于继承
复用现有节点、子场景、Resource 与公开信号，不新增不必要的深继承体系。

先查当前仓库、Godot 内建能力、现有插件与语言工具，最后才考虑新增最小必要实现。

涉及字体测量、Control 尺寸、CanvasItem 绘制、物理形状等 API 差异时，按 godot_mcp 查官方 4.7.2 文档。
### 9. 使用 Godot-MCP-Native 检查真实工程
涉及场景树/节点/Resource/信号则检查真实编辑器状态；运行时在 Godot 检查实际对象与 UI。

只运行与任务风险直接对应的最少量验证，复用仓库现有入口；视觉判断以真实画面为准。

延用稳定 Resource、信号和公开接口，不制造跨场景深层 NodePath 耦合。
### 12. 修改现有场景时尊重现有结构
检查场景实例、继承、UID、owner 与信号连接，做局部改动并保留已工作的流程。
### 13. 验证实际 Godot 行为
检查脚本解析、场景加载、本卡核心操作，执行一次目标运行并保存真实画面证据。

核对源码变更、真实效果、既有接口与流程、尺寸/输入/边界、遗留缺陷、PR 依赖与可追溯性。
